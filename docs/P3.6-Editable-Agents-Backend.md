# P3.6 — make agent rules genuinely editable & extensible (backend)

Frontend is updated (`frontend/index.html`): every agent's rules are now an edit/add/remove list,
and the Chief of Staff has a configurable persona/routing-guidance field (its adjudication core stays
locked). Make the backend honor this so it's real, not cosmetic.

1. **Config schema** — each agent config gains a free-text `rules` list (plain-English guidance) that is
   injected into that agent's LLM brief (system prompt), ALONGSIDE the existing structured/numeric
   thresholds (the deterministic hard signals). Adding/editing/removing a plain-English rule genuinely
   changes the agent's reasoning because it changes the brief — no code change needed. Numeric limits
   stay hard signals enforced in code. This split is the honest answer to "add any rule to any bucket."
2. **Endpoints** — extend the config API so the UI can PUT an agent's full config (rules list +
   thresholds) and re-run: `GET /agents/{id}/config`, `PUT /agents/{id}/config`, and the existing
   `/council/retest` re-evaluates against the saved config. All four agents, not just Finance/Operations.
3. **Chief of Staff** — accept an editable `persona` / `routing_guidance` string that feeds the CoS
   routing+reconcile brief; keep the adjudication policy (operational-blocker-wins), guardrails and
   bounded termination READ-ONLY / not user-settable. Persist the "what to flag" preferences.
4. **Validation** — plain-English rules are free but capped in count/length; numeric thresholds are
   range-checked; a malformed config is rejected, never silently applied. Persist per-agent config as
   the JSON that already backs the agents (so a fork ships with the defaults and users override).
5. **Tests** — adding a plain-English rule changes the agent's brief (assert it appears in the composed
   prompt); editing a numeric threshold changes the hard-signal outcome (existing config-swap test
   generalised to all four agents); CoS persona edit changes routing brief but CANNOT change the
   locked policy (adversarial test).

Acceptance: in the running app, open any agent in Council, add a plain-English rule, save, run a
scenario — the agent visibly reasons with the new rule. Edit a numeric limit — the hard-signal outcome
changes. The Chief of Staff's core stays locked throughout.

## Also in P3.6 — provider-aware model settings (the model / base-URL gap)

The Settings UI now adapts to the chosen provider (frontend already committed): for OpenAI / Anthropic /
OpenRouter the Base URL auto-fills and locks and the API key is required; for Local / self-hosted the
Base URL is editable and the key is optional. Make the backend honour this:

1. `PUT /settings/model` accepts `{provider, model, base_url, api_key}`. For hosted providers the server
   resolves the canonical base URL (ignore/override any client value); for local it takes the supplied
   base URL. Require a key for hosted providers; allow empty for local.
2. `POST /settings/model/test` runs a REAL connectivity check against the resolved endpoint+model+key
   (a tiny models-list or 1-token completion) and returns ok / the actual error. The UI's
   "Save & test connection" calls this — no fake success.
3. Persist to the server-side `.env` / config the run pipeline reads (model/llm.py already reads env).
   The whole app then reasons through whatever provider is configured — OpenAI-compatible throughout,
   so only base_url + key + model change between providers.
4. Test: a hosted provider ignores a bogus client base_url and uses the canonical one; a missing key on
   a hosted provider fails validation; local with no key still connects to the configured OSS endpoint.

Net: one PUT + one real test endpoint, and the provider dropdown genuinely reconfigures the running model.
