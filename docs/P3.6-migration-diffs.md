## One real bug the process caught before it reached this file (Delivery)

Not a logged "difference" — the process working as intended, not an approved
gap. My first rule design for Delivery's `conditional` stance used three
separate rules ("schedule improves but NOT `is_resourced`/`is_on_critical_
path`/`is_revenue_tagged`"), on the mistaken assumption those three flags
were the only way `evaluate()` could reach `conditional` while a schedule
improvement was happening. The golden run immediately surfaced 4 mismatches:
`reported_rag_before="red"`, `reported_rag_after="amber"`, with all three
flags `True` — a genuine schedule improvement (severity 2 → 1) whose Critical
Revenue at Risk doesn't actually change (both "red" and "amber" count as
`>=amber` for CRAR purposes), which `evaluate()` correctly scores
`conditional`, and my three narrower rules all missed because none of their
"not `<flag>`" clauses applied. Fixed by replacing the three rules with the
single true condition — `rag_after_severity < rag_before_severity and
crar_reduction <= 0` — before ever committing the migration, so this never
became a real difference to approve. See `backend/agents/delivery.py`'s
`schedule_improves_but_does_not_reduce_crar` rule and the commit `feat(agents):
migrate Delivery to rules[]` for the full account, and
`backend/tests/test_agent_delivery.py::test_rag_improving_within_the_same_
amber_or_red_bucket_is_still_conditional_not_yes` for the regression test
that pins it down permanently.

## Known, non-differential scope boundary (PMO)

`PMOConfig.adverse_direction` (which dimension's variance is adverse "over"
vs "under" its tolerance) is no longer read dynamically at check time — it's
baked into which `when` expression was authored per dimension in
`agents/configs/pmo.json` (e.g. `tv_cost > tol_cost` for an "over" dimension,
`tv_quality < neg_tol_quality` for an "under" one), since rules are
system-governed (§5.2) and the evaluator has no way to branch a comparison
operator by a runtime string value. This has **no effect on the golden
differential** (which only ever exercises the shipped default
`adverse_direction`, matching what's encoded in the rules) and no UI ever
exposed `adverse_direction` as an editable field, so it is not a behavioural
regression for anything a user could actually do — noted here for
completeness, not logged as a difference requiring approval.
